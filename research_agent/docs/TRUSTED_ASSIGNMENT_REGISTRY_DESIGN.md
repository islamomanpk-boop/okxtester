# Trusted assignment registry design (proposal only)

## Status and authority

Design proposal only. No registry, database, backend, credential, workflow, or dispatch channel is implemented or active. The Phase 3 G0-05 handoff remains controlling and prohibits the relevant execution, test, and workflow activity. This document grants no execution, dispatch, scheduling, repository-write, research, gate-closure, or phase-advancement authority.

The registry is a missing trust component between assignment-package preparation and assignment-return review. Its central purpose is to retain an immutable, independently trusted record of exactly what was approved and prepared, before a worker can receive it. A worker return must never be allowed to supply or replace the expected assignment.

## Trust boundary and ownership

The future system must keep these data classes separate:

1. **Trusted control data** — authenticated approval, task definition and digest, current handoff/policy snapshot, workflow identity, and registry state. Only the trusted dispatcher/store service may create or advance these records.
2. **Immutable assignment data** — canonical assignment package bytes (or an immutable content-addressed object), package digest, task digest, and assignment revision. The worker receives a copy, never write access to the retained original.
3. **Untrusted worker data** — returned submission, declared actions, findings, timestamps, evidence references, and any digest repeated by the worker. Store as an immutable raw return with its own receiver-computed digest; never use it as the expected package source.
4. **Verified review data** — structural/evidence review result tied to the trusted assignment revision and exact return digest. A passing review only permits human consideration.
5. **Human disposition data** — authenticated decision and actor from a trusted human-review channel. It is not inferred from workflow status, worker claims, or a successful review.

The worker must have no permission to read or modify approval records, expected package digests, delivery indexes, event-ledger checkpoints, or human dispositions. Prefer a separate service identity and storage boundary over relying only on hidden workflow variables.

## Minimum logical records

A backend may normalize these records into tables or equivalent transactional objects, but it must preserve the semantics and uniqueness constraints below.

### Assignment record

Required immutable identity fields:

- `assignment_id`: opaque unique identifier generated by the trusted dispatcher.
- `assignment_revision`: positive integer; revisions create new records and never overwrite earlier assignments.
- `task_id` and exact `task_definition_sha256`.
- `repository`, exact isolated `branch`, and pinned input `commit_sha`.
- `phase`, `operation`, `handoff_id` plus a stable handoff revision/content digest.
- Canonical assignment-package format/version, canonicalization version, exact package bytes or immutable object reference, and dispatcher-computed `package_sha256`.
- Exact workflow path and immutable workflow commit SHA, run ID, run attempt, and trusted triggering event identity.
- Authenticated approval-record ID and approval digest.
- Created-at timestamp from the trusted service.

Mutable lifecycle fields must be updated only through the state-transition transaction: current state, monotonically increasing state version, last event reference, and any terminal/reconciliation marker. Immutable identity and package fields must not be updated in place.

### Approval record

The approval is a separate immutable record, not a boolean input on the assignment. It must bind the authenticated human actor, approval timestamp, expiry/revocation state, repository, branch, workflow path and SHA, task ID and task digest, phase, operation class, handoff revision/digest, input commit, assignment scope/prohibitions, and the exact assignment/package digest when approval is package-specific.

Approval must be single-use for the exact operation it authorizes. A readiness-report approval cannot authorize worker delivery. Any change to task digest, package digest, workflow SHA, branch, handoff revision, scope, operation, or input commit invalidates the approval and requires a new authenticated decision. Revocation must be checked immediately before dispatch, not only when the approval is created.

### Delivery record

Keep delivery identity separate from assignment identity. Required fields include the authenticated provider/channel namespace, stable upstream delivery ID, assignment ID/revision, expected package digest, dispatch-attempt identity, trusted request timestamp, delivery state, and authenticated provider receipt/reference when one exists.

Enforce a durable unique provider-delivery identity on `(source_namespace, delivery_id)` and a separate event-level idempotency identity on `(source_namespace, delivery_id, event_role)` when one delivery legitimately produces multiple lifecycle events. The event role is closed and schema-defined. Enforce the provider's idempotency key where supported. A timeout must remain pending/unknown until reconciled; it must not create a new delivery identity or trigger an automatic retry.

### Return and review records

Each received return gets a receiver-generated immutable `return_id`, authenticated transport identity, linked assignment ID/revision and delivery identity, raw payload reference, receiver-computed raw-payload digest, and trusted receipt timestamp. The return's claimed task ID, assignment ID, package digest, and timestamps are untrusted fields to compare, not authority.

Each review record binds the exact assignment revision, exact raw-return digest, expected repository/branch/commit, evidence-manifest digest, verifier/reviewer version, outcome, and limitations. A review is superseded only by a new linked review record; never rewrite the historical result.

## State model and transition rules

Minimum assignment lifecycle:

- `prepared_not_dispatched`
- `dispatch_started`
- `delivery_pending_or_unknown`
- `delivery_confirmed`
- `submission_received`
- `review_completed`
- `human_disposition_recorded`

The registry must validate each transition against the authenticated prior state and expected state version. Unknown states, missing predecessor records, stale versions, and impossible transitions fail closed. The state machine is an audit lifecycle, not an execution permission engine.

| Transition | Required trusted evidence | Forbidden inference |
|---|---|---|
| create → prepared | Exact queued task, preflight/planner result, package bytes and digest, valid approval for preparation | Package preparation does not authorize delivery |
| prepared → dispatch_started | Fresh operation-boundary policy/handoff check, valid unexpired unrevoked delivery approval, durable delivery intent | A request being constructed is not delivery |
| dispatch_started → pending/unknown | Ambiguous timeout or lost response, recorded with same delivery identity | Uncertainty does not permit a second delivery |
| dispatch_started/pending → confirmed | Authenticated provider receipt bound to assignment and package digest | A successful HTTP/request response alone is insufficient unless provider semantics prove acceptance |
| confirmed → submission_received | Authenticated return channel and exact known delivery binding; raw payload retained | Worker-declared IDs or digest do not establish binding |
| received → review_completed | Structural review and evidence-byte/provenance verification tied to trusted checkout context | Review success is not task acceptance |
| reviewed → human disposition | Authenticated human decision tied to exact review and assignment revision | Worker or workflow cannot record human acceptance |

A human acceptance records task acceptance only. Phase-gate closure and phase advancement remain separate authenticated human decisions.

## Transaction and idempotency requirements

Every state transition must be a compare-and-swap transaction over the assignment's current state version, coupled atomically with its event-ledger append, delivery-index update (when applicable), and protected checkpoint advancement. The transaction must:

1. Authenticate the caller and derive actor/source identity from trusted transport context.
2. Load the assignment, approval, delivery record, event ledger, and protected checkpoint from the trusted store.
3. Verify immutable-record digests, event-chain integrity, checkpoint authenticity, and state-version consistency.
4. Revalidate the current task digest, branch, handoff revision, phase gate, global switches, allowlist, operation scope, and approval expiry/revocation at the protected operation boundary.
5. Apply one permitted state transition only; reject a stale expected version without side effects.
6. Enforce uniqueness and exact replay rules for the authenticated upstream delivery identity.
7. Atomically persist the new state version, event, delivery-index changes, and checkpoint; return a receipt only after commit.

If the transaction commits but its response is lost, a retry with the same authenticated idempotency identity must return the original receipt. If the same identity arrives with different assignment/package/task facts, reject it and preserve the original record. If the commit outcome cannot be established, mark the operation unknown and reconcile by the same identity before attempting anything else.

The assignment registry and event ledger must share one atomic transaction boundary, or the design must specify a separately proven transactional-outbox/inbox protocol. Merely writing a registry row and then separately appending an event is not sufficient.

## Package and digest rules

- The dispatcher computes the package digest from the exact canonical bytes it retains. The worker's copy is never authoritative.
- The canonicalization format and version must be explicit. The current Python JSON serialization is deterministic only under the documented pinned implementation; it is not automatically cross-language canonical JSON. Before a different runtime participates, adopt a versioned RFC 8785/JCS contract with shared test vectors or pin all writers/verifiers to one serializer/runtime.
- Store the exact package bytes or immutable content-addressed reference, not only the digest. A digest without retrievable expected bytes is insufficient for complete package comparison.
- The digest must cover the complete package, including task metadata, scope, prohibitions, handoff identity, allowed actions, submission schema, and authority flags.
- Recompute the digest when loading the package for delivery and return review. Verify that the retained bytes match the stored digest.
- A package change, even a seemingly harmless wording/schema change, creates a new assignment revision and requires fresh approval. Never mutate a package after approval.

## Revision, cancellation, expiry, and recovery

- A revision is a new assignment record linked to its predecessor, with a new package digest and fresh approval. The prior revision remains immutable and auditable.
- Cancellation/revocation is an authenticated event and state transition. It prevents future dispatch or acceptance but cannot erase an already-issued delivery or return record.
- Expiry is evaluated using trusted service time at the operation boundary. Expired approvals cannot be revived by replaying an earlier workflow input.
- If dispatch is uncertain, reconcile provider state and registry receipts using the original delivery identity. Do not automatically retry.
- If a worker returns after cancellation or expiry, preserve the raw return, mark it as late/revoked for review, and do not treat it as a valid completion.
- If registry, event chain, or checkpoint integrity fails, stop all transitions and require human investigation. Never reset or reconstruct the trust root from worker artifacts.
- Backup/restore must preserve assignment immutability, unique delivery identities, state versions, event order, and protected checkpoint lineage. A restored backup must be verified before any operation resumes. Restore acceptance must compare the exact registry/epoch/sequence/head-digest tuple to an independently authenticated witness, reject both stale and divergent snapshots, reconcile outstanding provider attempts by their original identities, and require independent human resume authorization. Missing revocation/consumption history must never be interpreted as an active approval.

## Access control, retention, and audit

- Use distinct least-privilege identities for dispatcher, worker, reviewer, human approver, and storage administrator.
- Worker identity may submit return bytes only; it must not write registry state or choose trusted metadata.
- Dispatcher may create prepared assignments and initiate only explicitly approved transitions; it must not self-approve.
- Reviewer may create review records but cannot create human dispositions or close phase gates.
- Human approver identity must come from an authenticated platform channel; a name typed into a workflow input is not identity proof.
- Protect approval, package, delivery, return, review, and checkpoint records against worker deletion or replacement.
- Define retention, backup, audit access, administrative break-glass, and incident response before selecting a backend.
- Avoid storing credentials, API keys, unnecessary personal data, or sensitive exchange account information in records or artifacts.

## Backend-neutral implementation gate

Do not select or configure a backend from this proposal alone. Evaluate any candidate against atomic multi-record transactions, unique constraints, authenticated service identities, immutable/content-addressed package storage, independent checkpoint protection, backup/restore, auditability, retention, and operational cost. A GitHub Actions artifact by itself is not a transactional registry. A repository file or branch commit is not automatically a trusted compare-and-swap store.

Before implementation, require:
1. Explicit approval of repository topology, backend, identity/access model, and retention.
2. A threat model covering compromised worker, compromised workflow, malicious repository change, stolen approval, replay, concurrent delivery, provider timeout, partial failure, administrator compromise, and backup rollback.
3. A failure-injection matrix for every transaction boundary and state transition.
4. Independent review of the schema, access controls, canonicalization, idempotency, and recovery behavior.
5. Confirmation that the controlling research handoff permits the exact implementation and validation scope.

No secrets, permissions, workflow triggers, schedules, VPS configuration, or research-branch changes are authorized by this design.

## Current implementation facts

- `assignment_package.py` builds an in-memory package; it does not persist the package or digest.
- `assignment_return.py` requires an independently supplied expected package digest, but no trusted dispatcher/registry currently retains that digest.
- `event_ledger.py` and `persistence_contract.py` are pure in-memory primitives; no durable store or protected checkpoint exists.
- `orchestration_coordinator.py` reports package digests with `package_digest_stored=False`; it does not dispatch.
- The trusted dispatcher and trusted-store documents describe related contracts; this document specifies the missing immutable assignment/approval/delivery registry records and transaction boundary.
- No backend, registry, delivery channel, worker dispatch, schedule, or unattended agent is active.
